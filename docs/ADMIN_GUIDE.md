# Руководство системного администратора ASS (Auto Segmentation System)

> **Версия системы:** 2.0.0+  
> **Целевая среда:** Локальная закрытая сеть отделения лучевой терапии (LAN / изолированный контур без интернета)  
> **Вычислительные ресурсы узлов:** Компьютеры с процессорами x86-64 и **16 ГБ оперативной памяти (CPU)**.

---

## 1. Архитектура системы и балансировка нагрузки

Комплекс **ASS** состоит из трех ключевых компонентов:
1. **Master-сервер (`ASS_Server`):**
   - Центральный узел координации, принимающий задачи сегментации КТ от рабочих станций врачей.
   - Управляет очередью задач (`QueueManager`), приоритетами, паузой и отменой расчетов.
   - Содержит **Центр локальных обновлений (Auto-Update Hub)** для автоматической раздачи новых версий клиентов по LAN.
   - Запускает **UDP Discovery Server** для мгновенного автопоиска сервера клиентами.
   - Включает **Диспетчер кластера (`ClusterManager`)**, распределяющий задачи по вычислительным воркерам.

2. **Вычислительные узлы — Воркеры (`ASS_Worker`):**
   - Дополнительные компьютеры отделения (например, свободные рабочие места врачей или выделенные ПК с 16 ГБ ОЗУ).
   - Запускаются в режиме `role = worker`.
   - Автоматически находят Master-сервер через UDP-broadcast и регистрируются в пуле узлов.
   - Принимают от Мастера архив КТ, выполняют ресурсоемкий инференс нейросетей TotalSegmentator в CPU-режиме, формируют RTSTRUCT и передают готовый архив обратно на Мастер.
   - **Мгновенная зачистка (HIPAA / 152-ФЗ):** сразу после передачи результата воркер гарантированно и безвозвратно удаляет все исходные DICOM-файлы и промежуточные маски пациента.

3. **Клиентские приложения (`ASS_Client`):**
   - Устанавливаются на рабочие места радиотерапевтов, медицинских физиков и рентгенлаборантов.
   - Обеспечивают удобный выбор серий КТ, пресетов органов (OAR), просмотр срезов в DICOM Viewer, отслеживание живого прогресса и очереди на сервере.
   - Не требуют установки тяжелых библиотек глубокого обучения (PyTorch / TotalSegmentator).

                      |       Клиенты ASS (Врачи / Физики)    |

                                          | HTTP (8000)
                                          | UDP Discovery (8001)
                                          v

                              |   MASTER-СЕРВЕР ASS   |

## 2. Особенности вычислений на CPU с 16 ГБ ОЗУ

Модель **TotalSegmentator** при инференсе на CPU выполняет высокое разрешение ресемплинга и обработку 117+ анатомических структур, потребляя **от 8 до 12 ГБ оперативной памяти в пике**.

* **Проблема при параллелизме на одной машине:** Запуск двух параллельных расчетов на одном физическом ПК с 16 ГБ ОЗУ неминуемо приведет к исчерпанию доступной памяти, уходу системы в своп (диск) или падению по Out-Of-Memory (OOM).
* **Решение ASS Cluster:**
  - Каждый узел кластера (как Мастер, так и каждый Воркер) обрабатывает **строго 1 задачу одновременно**, гарантируя нахождение потребления ОЗУ в безопасном диапазоне 8–11 ГБ.
  - Подключение двух ПК по 16 ГБ позволяет рассчитывать **2 КТ параллельно**. Подключение трех ПК — **3 КТ параллельно** (суммарный пул памяти 48 ГБ).

## 3. Сетевая топология и настройка брандмауэра (Firewall)

Для корректной работы компонентов в больничной локальной сети должны быть открыты следующие сетевые порты на Мастере и Воркерах:

| Протокол | Порт | Направление | Назначение |
|---|---|---|---|
| **TCP** | `8000` | Входящий на Master и Workers | REST API FastAPI: передача задач, получение RTSTRUCT, синхронизация пресетов, скачивание обновлений. |
| **UDP** | `8001` | Двунаправленный (Broadcast) | Zero-Config Auto-Discovery: автопоиск серверов ASS клиентами и воркерами в подсети. |

### Настройка Windows Firewall через PowerShell (на Мастере и Воркерах от Администратора):

```powershell
# Открытие TCP порта 8000 для API сервера ASS
New-NetFirewallRule -DisplayName "ASS Server API (TCP 8000)" -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow

# Открытие UDP порта 8001 для автообнаружения серверов (Zero-Config Discovery)
New-NetFirewallRule -DisplayName "ASS Auto-Discovery (UDP 8001)" -Direction Inbound -Protocol UDP -LocalPort 8001 -Action Allow
```

## 4. Развертывание и настройка вычислительного кластера

### 4.1. Запуск Master-сервера
На главном сервере в файле `config/server_settings.ini` задается:
```ini
[General]
cluster_role=master
dispatch_policy=offload_workers
use_gpu=false
```

Политики балансировки нагрузки (`dispatch_policy`):
* `offload_workers` (**Рекомендуется**): Задачи в первую очередь отдаются свободным воркерам. Мастер держит свой CPU свободным для обслуживания клиентов и GUI; локальный расчет на Мастере запускается только при нехватке воркеров.
* `dedicated_coordinator`: Мастер работает исключительно как координатор и никогда не запускает тяжелые расчеты у себя (идеально для слабых ПК).
* `first_available`: Задача отдается первому освободившемуся узлу (локальному или удаленному).

### 4.2. Подключение Worker-узла
**Способ 1 (Рекомендуется — Экспорт пакета из GUI):**
1. В интерфейсе Сервера (на вкладке **«⚡ Кластер»** или **«⚙️ Настройки»**) нажмите кнопку:
   `➕ Создать узел воркера...` / `➕ Создать пакет нового воркера...`.
2. Сервер автоматически проверит зарегистрированные узлы и вычислит следующий номер (например, `Worker-01`, `Worker-02`), сгенерирует уникальный ID и подставит сетевой IP Мастера.
3. Сохраните готовый архив `ASS_Worker_<Name>.zip`.
4. Архив содержит `config/server_settings.ini`, скрипт запуска `run_worker.bat`, скрипт настройки окружения `setup_worker.bat` и `README_WORKER.txt`.
5. Распакуйте архив на компьютере с 16 ГБ ОЗУ и запустите `run_worker.bat`. Воркер мгновенно появится в таблице кластера со статусом `🟢 Свободен`.

### 4.3. Управление узлами в реальном времени (1-Click Toggle)
В интерфейсе Сервера во вкладке **«⚡ Кластер»** в таблице отображаются все подключенные узлы с их системными метриками (ОЗУ, CPU, пинг, статус).
* В крайней правой колонке **«Управление»** для каждого удаленного воркера доступна кнопка быстрого управления:
  * **`⏸️ Отключить`**: переводит узел в статус `⏸️ Отключен (DISABLED)`. Воркер остается на связи и шлет пинги, но Мастер временно исключает его из очереди распределения задач (удобно, если за ПК временно сел пользователь или планируются работы).
  * **`▶️ Включить`**: мгновенно возвращает узел в рабочий пул (`🟢 Свободен`).

### 4.4. Скрытый запуск и автозагрузка воркера (Background Service Mode)
Чтобы узел работал автономно в фоне без всплывающего черного консольного окна:
1. **Скрытый запуск вручную**: используйте `run_worker_no_console.bat` вместо обычного `run_worker.bat`. Он запускает службу через тихий интерпретатор `pythonw.exe`.
2. **Автозагрузка при старте Windows**: запустите скрипт `add_to_startup.bat` от имени обычного пользователя. Скрипт создаст ярлык тихой автозагрузки в каталоге `shell:startup`. Теперь при каждом включении компьютера воркер будет автоматически и незаметно для пользователя подключаться к Серверу.
3. **Удаление из автозагрузки**: при необходимости отключения автозапуска запустите `remove_from_startup.bat`.

## 5. Развертывание клиентов (Zero-Configuration Deployment)

Администратор может развернуть клиент на рабочем месте врача за **30 секунд** без ручного ввода IP-адресов.

### Способ 1: Экспорт преднастроенного архива в 1 клик из GUI Сервера (со сборкой на лету)
1. В интерфейсе Сервера перейдите в **«⚙️ Настройки»** -> раздел **«Раздача обновлений клиентам»**.
2. Нажмите кнопку **«📦 Экспорт преднастроенного клиента для этой сети...»**.
3. При необходимости сервер предупредит, если исходный код `client_app.py` изменился, и предложит вариант:
   - `🚀 Скомпилировать и упаковать`: компилирует свежий `ASS_Client.exe` через PyInstaller в модальном окне с живым логом, регистрирует новую версию и упаковывает архив.
   - `⚡ Использовать существующий EXE`: мгновенная упаковка уже скомпилированного бинарника.
4. Сервер генерирует готовый архив `ASS_Client_Configured_<IP>.zip`, содержащий `client_settings.ini` с уже прописанным адресом Мастера.
5. Распакуйте архив на ПК врача — клиент готов к работе сразу после запуска.

### Способ 2: UDP Auto-Discovery (Автопоиск в сети)
1. Если клиент запущен со стандартными настройками (`127.0.0.1:8000`) и не видит локального сервера:
2. Клиент **автоматически отправляет широковещательный UDP-запрос** в сеть, находит Master-сервер и подставляет его IP-адрес.
3. Врач также может кликнуть на индикатор `Сервер: ❌` в правом верхнем углу и нажать кнопку **«🔍 Автопоиск»**.

## 6. Локальный центр обновлений (Centralized Auto-Update Hub)

В закрытом медицинском контуре без доступа к сети Интернет клиенты обновляются централизованно через Master-сервер.

### Процедура выпуска обновления:
1. Администратор компилирует или получает новый бинарный файл `ASS_Client.exe`.
2. В окне Сервера на вкладке **«⚙️ Настройки»** в секции **«📦 Раздача обновлений клиентам»** нажимает кнопку **«Загрузить новый ASS_Client.exe на сервер...»**.
3. Указывает версию (например, `2.1.0`) и примечания к релизу.
4. Бинарный файл сохраняется в `updates/client/` на сервере.

### Поведение на рабочих местах врачей:
* Клиент периодически опрашивает статус сервера.
* При обнаружении новой версии в правом верхнем углу интерфейса клиента появляется ненавязчивая зеленая кнопка:
  `🔄 Обновить (v2.1.0)`.
* Обновление скачивается **в фоновом режиме** без прерывания работы врача.
* Врач нажимает кнопку в удобный момент (например, между пациентами). Клиент мгновенно перезапускается уже обновленным (`updater.bat` заменяет `.exe` с сохранением всех персональных настроек).

## 7. Интеграция с Elekta Monaco TPS и PACS

1. **Экспорт RTSTRUCT:**  
   Сформированные файлы структуры `STR_YYYYMMDD_HHMMSS.dcm` полностью совместимы с требованиями спецификации DICOM 3.0 и Elekta Monaco:
   - Соблюдаются строгие теги `FrameOfReferenceUID`, `PositionReferenceIndicator`, `PatientPosition`.
   - Контур всего тела автоматически маркируется интерпретированным типом `BODY` с описанием `Type:Body` для корректного расчета дозиметрической матрицы.
   - Органы риска маркируются типом `ORGAN` с описанием `Type:Soft`.
2. **Папка импорта Monaco:**  
   На клиенте ASS в поле «Папка сохранения RTSTRUCT» указывается локальная папка импорта пациента Monaco или сетевая папка обмена (например, `\\monaco-server\patients\...\`).

## 8. Мониторинг, логирование и безопасность

* **Логи сервера:** сохраняются в `server/server.log` (или консоль с ротацией).
* **Логи клиента:** сохраняются в папке `logs/`.
* **Защита от сбоев (Failover):** если вычислительный узел внезапно отключился во время расчета, Мастер регистрирует таймаут heartbeat (15 секунд), переводит узел в `⚪ Офлайн` и возвращает задачу в очередь со статусом ошибки или на перерасчет.
* **Черный список:** Администратор сервера может в 1 клик временно заблокировать клиента по имени или IP в таблице активных подключений.
